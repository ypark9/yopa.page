Claude Code의 Agent Teams는 여러 Claude Code 세션을 하나의 팀으로 묶는다. 팀 리드가 일을 나누고, 각 teammate는 별도의 컨텍스트에서 작업하며, shared task list와 메시지로 진행 상황과 발견한 내용을 공유한다.

중요한 점은 세션 수를 늘리는 기능 자체가 아니다. 서로 독립적으로 진행할 수 있는 일을 병렬화하면서도, 작업 사이의 계약과 검증 책임을 잃지 않는 데 가치가 있다. 순차 작업이나 같은 파일을 고치는 일에 팀을 붙이면 속도보다 조정 비용이 더 커진다.

## 먼저, 팀이 필요한 작업인지 판단한다

Agent Teams를 쓰기 전에 작업을 세 가지로 구분하면 선택이 쉬워진다.

- 한 세션이 도구를 써서 끝낼 수 있는 일은 그대로 한 세션에 맡긴다.
- 조사나 테스트처럼 결과만 돌려받으면 되는 독립 작업은 subagent가 가볍다.
- 여러 작업자가 중간 결과를 주고받거나 서로의 가설을 반박해야 한다면 Agent Teams가 맞다.

공식 문서가 제시하는 좋은 사례도 병렬 조사와 리뷰, 서로 다른 가설을 시험하는 디버깅, 프론트엔드·백엔드·테스트처럼 소유권을 나눌 수 있는 구현이다. 반대로 단계가 강하게 연결된 작업, 작은 수정, 같은 파일을 함께 편집하는 작업에는 맞지 않는다.

판단 기준을 한 문장으로 줄이면 이렇다. **작업을 독립된 결과물로 나눌 수 있고, 작업자끼리 중간 발견을 공유해야 하는가?** 두 조건이 모두 맞을 때 팀을 만든다.

## 실험 기능을 켜고 작은 팀부터 시작한다

Agent Teams는 Claude Code 2.1.32 이상에서 사용할 수 있으며, 현재 실험 기능이라 기본으로 꺼져 있다. `settings.json`에 다음 환경 변수를 추가한다.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

버전은 다음 명령으로 확인할 수 있다.

```bash
claude --version
```

팀 구성은 별도 설정 파일을 직접 만들기보다 자연어로 요청하는 방식이 기본이다. 처음에는 리드 한 명과 teammate 두세 명이면 충분하다.

```text
이 인증 오류를 세 가지 독립 가설로 조사할 agent team을 만들어라.

- protocol: OAuth 흐름과 토큰 검증 경로 조사
- runtime: 최근 로그와 환경 설정 조사
- skeptic: 두 가설의 증거를 반박하고 재현 절차 검토

각 teammate는 파일을 수정하지 말고 근거, 반증 조건, 다음 실험을 리드에게 보내라.
리드는 결과를 비교한 뒤 가장 값싼 검증 실험 하나만 실행하라.
```

팀 리드는 이 요청을 바탕으로 teammate를 만들고 shared task list를 관리한다. in-process 모드에서는 `Shift+Down`으로 teammate를 전환해 직접 메시지를 보낼 수 있다. tmux나 iTerm2를 사용하면 split-pane으로 각 세션을 따로 볼 수도 있다.

## 역할보다 산출물의 경계를 먼저 쓴다

`frontend`, `backend`, `test`처럼 역할 이름만 주면 경계가 모호하다. 각 작업에는 다음 항목이 있어야 한다.

- 목표와 완료 조건
- 읽거나 수정해도 되는 파일 범위
- 다른 teammate에게 넘겨야 할 인터페이스
- 실행할 검증 명령
- 막혔을 때 보고할 증거

예를 들어 API 기능을 나눈다면 백엔드 teammate의 산출물을 “API를 구현한다”로 두지 않는다. “라우트와 응답 스키마를 구현하고, 변경된 계약과 테스트 결과를 frontend와 test teammate에게 보낸다”처럼 쓴다. 프론트엔드는 그 계약을 받은 뒤 호출 코드를 바꾸고, 테스트 담당은 양쪽 구현을 독립적으로 검증한다.

이 방식은 메시징을 대화가 아니라 계약 전달에 사용하게 만든다. teammate가 긴 작업 로그를 그대로 보내는 대신, 다른 작업자의 다음 결정을 바꿀 정보만 보내도록 한다.

```text
계약 변경: POST /sessions 응답에 expires_at 추가
근거: api/openapi.yaml, server/session.ts
영향: web/session-client.ts 타입 갱신 필요
검증: backend unit tests 통과
미확인: timezone 표시 방식은 제품 결정 필요
```

## 메시지는 상태 보고가 아니라 의존성 해소에 쓴다

Agent Teams에는 teammate 간 메시징과 shared task list가 있다. 둘의 용도를 섞지 않는 편이 좋다.

- task list에는 소유자, 상태, 선행 작업, 완료 여부를 둔다.
- 메시지에는 새로 발견한 계약, 반례, 차단 요인, 의사결정 요청을 담는다.
- 단순히 “작업 중”이라는 메시지는 보내지 않는다.
- 모든 메시지는 받는 사람이 무엇을 해야 하는지 드러나게 쓴다.

의존성이 있는 작업은 shared task list에 명시한다. 선행 작업이 끝나면 뒤 작업이 풀리므로, teammate가 메시지를 반복해서 확인하며 대기할 필요가 없다. 작업 상태가 실제 결과보다 늦게 갱신될 수 있는 실험 기능의 한계가 있으므로, 리드는 완료 표시만 믿지 말고 산출물과 검증 결과를 확인해야 한다.

## 같은 파일을 함께 고치지 않는다

Agent Teams의 teammate는 별도 컨텍스트를 쓰지만 자동으로 별도 worktree를 쓰는 것은 아니다. 같은 checkout에서 같은 파일을 수정하면 변경을 덮어쓰거나 서로의 미완성 코드를 전제로 작업할 수 있다.

안전한 분할은 파일 소유권이 겹치지 않는다.

```text
backend: server/**, api/openapi.yaml
frontend: web/**
tests: tests/integration/** (제품 코드는 읽기 전용)
lead: 최종 통합과 공통 설정 파일
```

공통 타입이나 lockfile처럼 여러 작업이 건드릴 파일은 리드가 마지막에 통합한다. 파일 경계를 만들 수 없다면 병렬 편집 대신 조사와 리뷰만 병렬화하거나, 격리가 필요한 세션에는 worktree를 사용한다.

## 리드는 직접 구현하기보다 결정을 관리한다

팀 리드의 역할은 가장 많은 코드를 쓰는 것이 아니다. 좋은 리드는 다음 네 가지를 관리한다.

1. 작업이 실제로 독립적인지 확인한다.
2. teammate의 발견을 필요한 대상에게 전달한다.
3. 충돌하는 결과를 추가 실험이나 리뷰로 해소한다.
4. 전체 변경에 대해 한 번 더 통합 검증을 실행한다.

특히 리드에게 “teammate가 끝날 때까지 기다린 뒤 종합하라”고 명시하는 편이 안전하다. 현재 Agent Teams는 리드가 작업 완료를 너무 일찍 판단하거나 teammate의 상태 표시가 늦어지는 경우가 있다. 완료 조건에는 모든 teammate의 응답, 실제 diff, 테스트 결과를 함께 넣는다.

## 효과가 큰 세 가지 패턴

### 경쟁 가설로 디버깅하기

한 오류를 로그, 데이터, 네트워크처럼 나눠 보는 대신 서로 다른 원인 가설을 맡긴다. 각 teammate가 자기 가설을 입증하는 것뿐 아니라 기각할 조건도 제출하게 한다. 리드는 세 결과를 모아 가장 판별력이 높은 실험부터 실행한다.

### 구현과 반대 관점 리뷰를 동시에 하기

한 teammate가 구현하고 다른 teammate가 같은 코드를 따라 쓰게 하지 않는다. 구현자는 기능을 만들고, 리뷰어는 보안·성능·실패 복구처럼 다른 관점에서 요구사항과 diff를 검토한다. 두 작업은 독립적이면서 메시지를 주고받을 이유가 분명하다.

### 여러 레이어를 계약으로 나누기

프론트엔드, 백엔드, 테스트를 파일 경계로 나누고 API 스키마나 이벤트 형식을 메시지로 공유한다. 리드는 계약 변경을 승인하고 최종 통합 테스트를 맡는다. 레이어 사이의 의존성이 너무 많다면 먼저 계약을 확정한 뒤 병렬 구현을 시작한다.

## 비용과 현재 한계를 운영 규칙에 넣는다

Agent Teams는 teammate마다 독립된 컨텍스트를 사용하므로 팀 크기에 비례해 토큰 사용량이 늘어난다. 팀은 작게 유지하고, teammate의 시작 프롬프트에는 필요한 범위와 산출물만 넣는다. 단순한 일에 팀을 쓰지 않는 것이 가장 효과적인 비용 절감법이다.

현재 공식 문서가 밝히는 주요 한계도 있다.

- in-process teammate는 `/resume`이나 `/rewind`로 복원되지 않는다.
- task 상태가 실제 작업보다 늦게 갱신될 수 있다.
- teammate 종료는 진행 중인 요청이나 도구 호출이 끝날 때까지 늦어질 수 있다.
- 한 세션은 한 팀만 관리할 수 있고 nested team은 지원하지 않는다.
- 팀 리드는 도중에 바꿀 수 없다.
- split-pane은 지원되는 터미널과 tmux 또는 iTerm2가 필요하다.

따라서 장시간 지속되는 워크플로의 상태 저장소로 Agent Teams를 사용하면 안 된다. 커밋, 이슈, 테스트 결과, 설계 문서처럼 세션 밖에 남는 산출물을 기준으로 복구 가능성을 만든다.

## 시작할 때 쓸 체크리스트

- 한 세션이나 subagent보다 팀이 나은 이유를 한 줄로 썼는가?
- teammate별 파일과 산출물 경계가 겹치지 않는가?
- shared task list에 의존성과 완료 조건이 있는가?
- 메시지는 다음 결정을 바꾸는 정보만 담는가?
- 리드가 모든 결과를 기다리고 통합 검증하도록 지시했는가?
- 중단 후에도 복구할 수 있는 산출물이 저장소에 남는가?
- 추가 토큰 비용을 감수할 만큼 병렬화의 가치가 있는가?

Agent Teams를 잘 쓰는 핵심은 에이전트를 많이 띄우는 데 있지 않다. 독립적으로 진행할 일은 분리하고, 연결되는 지점은 명시적인 계약으로 만들며, 최종 판단은 리드에게 모으는 것이다. 이 구조를 먼저 만들 수 있을 때 세션 간 메시징이 실제 생산성 기능이 된다.

기능의 최신 설정과 제한은 Claude Code 공식 문서의 [Agent Teams 가이드](https://code.claude.com/docs/en/agent-teams)와 [병렬 에이전트 선택 가이드](https://code.claude.com/docs/en/agents)에서 확인할 수 있다. 더 일반적인 구조 선택 기준은 [에이전트가 하나로 부족할 때만 멀티에이전트를 설계하라](/blog/2025-12-12-designing-robust-multi-agent-systems.html)에서 다뤘다.
