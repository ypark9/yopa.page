에이전트는 모델 하나로만 정의되지 않는다. 사용할 도구, 시스템 프롬프트, 맡은 역할, 다른 작업을 넘길 대상이 함께 에이전트의 동작을 만든다. 따라서 중요한 질문은 “무엇을 넣을 것인가”만이 아니다. 그 구성을 언제 확정할지, 그리고 실행 중에 누가 바꿀 수 있는지도 설계의 일부다.

이 글에서 말하는 바인딩 시점은 바로 그 결정 시점이다. 세션을 시작할 때마다 구성을 조립할지, 설치 단계에서 미리 배치할지를 두고 흔히 유연성과 단순성의 취향 문제로 생각한다. 실제 기준은 더 단순하다. 에이전트를 실행하는 런타임을 직접 소유하는지다.

에이전트를 몇 개로 나누고 어떻게 협업시킬지는 그다음 문제다. 이 주제는 [멀티 에이전트 시스템 설계 글](/blog/2025-12-12-designing-robust-multi-agent-systems.html)에서 다뤘다. 여기서는 그보다 앞선 단계, 즉 에이전트 하나의 구성을 언제 정할지를 살펴본다.

## 두 가지 바인딩 시점

```
늦은 바인딩   세션이 시작될 때마다 구성을 조립한다.
             하나의 프로세스가 여러 세션을 실행하며,
             세션마다 서로 다른 에이전트 구성을 사용할 수 있다.

이른 바인딩   설치 또는 setup 단계에서 구성을 대상에 미리 반영한다.
             파일, 심링크, 훅을 checkout에 배치하는 방식이다.
             구성을 바꾸려면 setup을 다시 실행해야 한다.
```

늦은 바인딩은 유연하다. 장기 실행 프로세스에 여러 구성을 등록해 두고, 세션마다 필요한 구성을 선택할 수 있다. 같은 프로세스 안에서 벤치마크용 최소 에이전트와 모든 기능을 갖춘 코딩 에이전트를 함께 운영하는 것도 가능하다.

이른 바인딩은 단순하다. setup 단계에서 필요한 파일과 훅을 배치하고, 다른 구성이 필요하면 setup을 다시 실행한다. 그렇다고 뒤처진 설계라는 뜻은 아니다. 많은 환경에서는 늦은 바인딩을 선택하지 않는 것이 아니라, 애초에 구현할 수 없다.

## 선택을 결정하는 것은 런타임 소유권이다

늦은 바인딩을 구현하려면 실행 중인 세션에 구성을 연결할 지점이 필요하다. 런타임 안에서 도구, 프롬프트, 위임 대상을 세션 시작 때 추가하고 종료할 때 제거할 수 있어야 한다.

런타임을 직접 만들고 운영한다면 이런 연결 지점을 설계할 수 있다. 세션의 정의, 구성의 등록 위치, 적용과 정리 시점을 모두 통제할 수 있기 때문이다. 늦은 바인딩이 가능한 이유는 구성을 바꾸는 장치까지 함께 소유하기 때문이다.

반대로 다른 회사나 프로젝트가 만든 에이전트에 도구를 추가하는 경우에는 상황이 다르다. 그 에이전트의 프로세스, 세션 수명주기, 도구 등록 방식은 내 것이 아니다. 세션 시작 시 구성을 주입할 내부 지점에 접근할 수 없다.

이때 할 수 있는 일은 에이전트가 읽을 수 있는 형식으로 구성을 만들고 정해진 위치에 배치하는 것이다. 설정 파일을 작성하고, 훅과 심링크를 두고, checkout에 설치 상태를 기록한다. 이것이 이른 바인딩이다. 구현 능력의 문제가 아니라 런타임의 내부 연결 지점을 소유하지 않기 때문에 생기는 제약이다.

여러 벤더의 코딩 에이전트가 같은 오케스트레이션 도구를 사용하도록 확장하면서 이 차이를 확인한 적이 있다. 공통 컨텍스트를 각 에이전트가 읽는 형식으로 렌더링하는 일은 가능했다. 그러나 실제 동작을 정하는 훅과 설정 규칙은 벤더마다 달랐다. 같은 내용을 두 파일로 만든다고 해서 두 에이전트가 같은 방식으로 작동하지는 않았다. 결국 공통 문서와 벤더별 실행 설정을 분리해야 했다.

**늦은 바인딩은 직접 소유한 런타임 안에서만 가능하다. 런타임을 소유하지 않는다면 이른 바인딩이 현실적인 상한선이며, 여러 에이전트가 공유할 수 있는 것은 실행 동작이 아니라 렌더링된 문서다.**

## 늦은 바인딩에 따르는 비용

런타임을 소유하면 늦은 바인딩을 구현할 수 있다. 그러나 이 유연성에는 수명주기와 권한 관리 비용이 따른다.

- **세션 종료 시 구성을 반드시 정리해야 한다.** 세션마다 구성을 할당했다면 종료할 때 해제하는 과정도 필요하다. setup만 만들고 teardown을 빠뜨리면 끝난 세션의 구성이 메모리에 남는다. idle eviction은 나중에 추가할 편의 기능이 아니라 처음부터 수명주기에 포함해야 할 기능이다.
- **재개한 세션은 처음 사용한 구성을 복원해야 한다.** 지난주에 만든 세션을 오늘 다시 열 때 오늘의 기본 구성을 적용하면 안 된다. 세션이 어떤 구성으로 만들어졌는지 기록하고, resume할 때 그 구성을 다시 조립해야 한다.
- **구성이 자기 자신을 대상으로 적용되지 않도록 막아야 한다.** 구성을 세션 범위에 붙이는 대상과 구성 자체가 같아지는 경우는 별도로 거부해야 한다.
- **구성 작성은 높은 권한이 필요한 작업이다.** 구성은 세션이 사용할 코드와 도구를 결정한다. 세션을 시작할 수 있다는 이유만으로 누구나 구성을 변경할 수 있어서는 안 된다.

이른 바인딩은 유연성이 낮은 대신 런타임에서 관리할 상태가 적다. 세션마다 추가·제거할 구성도 없고, 재개할 때 과거 정체성을 복원할 필요도 없다. 선택 기준은 유연함과 단순함 중 무엇이 더 좋아 보이는지가 아니라, 필요한 유연성을 위해 이 운영 비용을 감당할 이유가 있는지다.

## 결정 순서

1. **세션을 실행하는 런타임을 직접 소유하는가?** 아니라면 이른 바인딩을 기준으로 설계한다. 구현할 수 없는 실시간 교체 기능을 흉내 내기보다, 생성되는 파일을 명확히 하고 setup을 빠르고 반복 가능하게 만드는 편이 낫다.
2. **세션마다 실제로 다른 구성이 필요한가?** 런타임을 소유하더라도 모든 세션이 같은 에이전트를 사용한다면 늦은 바인딩은 필요 없다.
3. **늦은 바인딩의 운영 비용을 처음부터 반영했는가?** 구성 정리, resume 복원, 자기 자신을 대상으로 하는 구성 차단, 작성 권한 통제는 기본 설계의 일부다.

## 실제 적용 방법

늦은 바인딩을 무조건 더 나은 목표로 볼 필요는 없다. 이른 바인딩과 늦은 바인딩은 서로 다른 소유 조건에 맞춘 설계다.

런타임을 소유하고 세션마다 다른 구성이 필요하다면 늦은 바인딩을 구현한다. 이때 setup과 teardown을 함께 만들고, 세션이 어떤 구성으로 시작했는지 영속적으로 기록하며, 구성 변경 권한을 분리한다.

런타임을 소유하지 않았다면 존재하지 않는 주입 지점을 억지로 흉내 내지 않는다. 대신 에이전트가 읽을 파일을 일관되게 렌더링하고, setup을 멱등적이고 빠르게 만든다. 여러 벤더를 지원할 때는 공통 컨텍스트보다 각 런타임의 훅과 설정 규칙을 맞추는 일이 더 큰 작업이라는 점도 계획에 반영해야 한다.

추상화가 더 깔끔해 보인다고 해서 구현 가능한 것은 아니다. 먼저 통제할 수 있는 경계를 확인해야 한다. 그 경계를 모른 채 구성 방식부터 선택하면, 실제 런타임에는 붙일 곳이 없는 기능을 설계하게 된다.

구성을 마친 에이전트들이 실행된 뒤 서로 정보를 주고받는 방법은 별개의 문제다. 구체적인 사용법은 [Claude Code 세션 간 메시징 글](/blog/2026-08-10-claude-code-cross-session-messaging.html)에서 다뤘다.
